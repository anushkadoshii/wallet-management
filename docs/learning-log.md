# Learning log

Three lines a day: what I learned, what broke, what I'd do differently.

## Day 1 · Nov 10: Setup + double-entry on paper
- Learned: Every money movement is one entry whose postings sum to zero. Money enters only via BANK_CLEARING (top-up) and leaves only via a completed payout. A withdrawal needs two entries because PAYOUTS_IN_FLIGHT holds the money while the bank hasn't answered yet. System accounts like BANK_CLEARING can go negative (−₹400 means ₹400 from outside is inside Kosh); wallets can't.
- Broke: Nothing major. I don't need IntelliJ/DBeaver/Bruno: VS Code's Java, Spring Boot, SQLTools and REST Client extensions cover them, and every Spring project ships its own Maven wrapper (`mvnw`).
- Next time: Push the repo to GitHub the same day, not later.

## Day 2 · Nov 10: Java for Spring (records, enums, streams, exceptions)
- Learned: Records give immutable data classes for free (good fit for postings, which must never change). Enums turn typos into compile errors. `flatMap` turns "list of entries, each with a list of postings" into one stream; `groupingBy` + `summingLong` computes every balance in one line, which is the code version of "a balance is the sum of its postings". `Math.addExact` throws on overflow instead of silently wrapping. Exceptions are objects: `throw new ...`, and nothing after a `throw` can run.
- Broke: (1) `throw IllegalArgumentException(...)` without `new` and an unreachable `return` after it: compile errors. (2) VS Code kept reporting a build failure from an old, half-typed version of `AccountType.java` even though Maven compiled fine; fixed with "Java: Clean Java Language Server Workspace". (3) Logic bug: `sum += amount` was inside the `if (amount == 0)` block, so the sum stayed 0 and the zero-sum check could never fail. It compiled and looked fine; only a deliberately broken entry would have caught it.
- Next time: For every rule I write, also write one input that should break it and check that it does (same idea as the break-it experiments). If Maven and VS Code disagree, trust `mvnw` and clean the VS Code Java workspace.

## Day 3 · Nov 11: Maven, JUnit 5, Spring dependency injection
- Learned: JUnit tests replace reading `println` output: `assertThrows(Ex.class, () -> code)` takes a lambda so JUnit can run the code inside its own try/catch, and checking the message proves it failed for the right reason. Spring DI: classes declare what they need in their constructor and Spring passes in the bean, so the controller never creates or chooses its calculator; that keeps them loosely coupled (swap implementation or pass a fake in tests without touching the controller). This works for any Spring-managed class, not just controllers. Half-up rounding in integer paise: `(amount × bps + 5000) / 10000`, with `multiplyExact` against overflow.
- Broke: (1) `assertThat` undefined: forgot its static import from `org.assertj`. (2) My first fee version added 1 for any remainder; that's ceiling rounding (1.49 → 2), which would overcharge merchants. Fix: round up only when the remainder is ≥ 5000 (half of 10,000). (3) My first explanation of DI said "because it's a RestController"; wrong reason, DI applies to any bean.
- Next time: Check rounding logic against values just below, at and above .5 before trusting it. When explaining a concept, answer "why" (what goes wrong without it), not just "how".

## Day 4 · Nov 12: REST APIs, validation, error handling, MockMvc
- Learned: `@RestControllerAdvice` + `@ExceptionHandler` turn exceptions into clean JSON errors with the right status, so controllers stay free of try/catch. `@Valid` + annotations like `@NotBlank`/`@Positive` on request records reject bad input before my code runs. Separate request/response records (DTOs), because the client must not choose the wallet id. `POST` returns **201 + Location header** via `ResponseEntity.created(...)`; transfer returns **204**. **400** means the request is wrong on its own (blank owner, zero amount, sending to yourself); **422** means it is well-formed but conflicts with current data (not enough balance), and only checking the data reveals it. `@WebMvcTest` loads just the web layer: 0.9 s vs 5.7 s for the full app. Design choice: amounts are whole numbers in the smallest currency unit, so there is never floating-point rounding.
- Broke: (1) Before the handler, a negative fee gave a 500, which blamed the server for the client's mistake. (2) In `transfer`: `wallets.put(null, receiver)` used the wrong key, had no `;`, and never saved the sender, so money would have appeared without leaving anyone. (3) Sending to the same wallet **created money**: `from` and `to` were the same old copy, so the second `put` (1000 + 100) overwrote the first (1000 − 100) and the wallet ended at 1100. Fixed with a `fromId.equals(toId)` check → 400. (4) In the test I used a non-existent `transfer(...)` request builder and left a dangling `.`; a transfer is just `post("/transfers")`.
- Next time: Whenever code reads two things and writes both back, ask "what if they are the same thing?" When a method returns a value (like `create`), keep it if I'll need it later. Still open: the transfer isn't safe under concurrent requests (Day 16).

## Day 5 · Nov 13: SQL + PostgreSQL by hand (constraints, transactions, row locks)
- Learned: Postgres 16 in Docker (`docker run`, `docker exec -it ... psql`). Hand-wrote `account`, `journal_entry`, `posting`, `balance` with PK, FK, UNIQUE and CHECK constraints, and seeded them with `INSERT ... SELECT`. Constraints are the last line of defence, even when the app has a bug: `request_id UNIQUE` blocked a retried top-up (idempotency), and `no_overdraft` blocked Ravi going to −4700 when I forgot the guard. `posting.amount <> 0`, not `> 0`, because debits are negative. The `balance` table is a fast running total of the postings, and the invariant check confirms they match. **The conditional update** `WHERE posted - held >= :a` returning **`UPDATE 0`** is not an error; it means "not enough money", and the code must `ROLLBACK`, or the postings record a move the balances never made. **Row locks (two terminals):** the second `UPDATE` on the same row waits for the first to commit, then **re-checks its `WHERE` on the new value** (Read Committed): 700 → 200, so the second 500 gets `UPDATE 0` and nothing overdraws. **Lost update:** read the balance (both see 200), compute in the app, write `posted = 100` (both write 100). Two withdrawals of 100 removed only 100, so 100 was created. The CHECK didn't help, because 100 is a valid balance. This is exactly what my Java `WalletService.transfer` does.
- Broke: (1) Schema mistakes: a missing comma; account types in the entry-type CHECK; `amount > 0`; `UNIQUE` on `posting(entry_id)` (which allows only one posting per entry); `GENERATED IDENTITY` on `balance.account_id`. UNIQUE is a business rule, not a speed-up. (2) A missing `;` after `CREATE TABLE balance`, which didn't show until another statement followed it. (3) `ROLLBACK` without `;` merged with the next line. (4) Used `"..."` for text and an unclosed `'`; text values use single quotes, while double quotes are for column and table names. (5) A failed insert still used up entry id 3: IDs have gaps, so read `RETURNING id`, never guess.
- Next time: Read the psql prompt: `=` ready, `!` failed transaction (type `ROLLBACK;`), `*` inside a transaction, `-` or `'` waiting for more input. Never "read, compute in Java, write a number back" for money; do the maths inside one guarded `UPDATE`.

## Day 6 · Nov 14: Spring Data JPA + Flyway
- Learned: The wallet app now stores data in Postgres (`sandbox_db`), so it survives restarts. **Flyway** owns the schema: `V1__ledger_core.sql` (the Day 5 tables) and `V2__wallet.sql` run once each, in order, and are recorded with a checksum in `flyway_schema_history`. **Never edit a migration that has already run**; to change the schema, add `V3__...`. **`ddl-auto=validate`**: Hibernate only checks that the entities match the tables and refuses to start if they don't (a renamed field gives "missing column"). `update` would quietly add an empty column, so balances would appear as 0. A failed startup is better than wrong money. **`@Entity`** can't be a record, because JPA needs a no-arg constructor, mutable fields and a non-final class (Hibernate builds the object from a row, then fills in the fields, and may subclass it as a proxy). `debit`/`credit` instead of `setBalance`. **`JpaRepository`** gives `save`/`findById` for free; `findByOwner` gets its SQL from the method name. **Entity vs DTO:** the service works with `Wallet` and the controller only sees `WalletResponse`. **`@Transactional`:** everything in the method commits or rolls back together. A runtime exception rolls it back; a checked exception does *not* by default. **Dirty checking:** inside a transaction, loaded entities are "managed", and at commit Hibernate compares them with what it loaded and writes UPDATEs for the changes. That's why `transfer` needs no `save()`. **Without `@Transactional`**, each repository call is its own mini-transaction: `save(from)` commits at once, so a crash before `save(to)` makes the money vanish (the sender is debited and the receiver never credited). In tests, `@SpringBootTest` + `@AutoConfigureMockMvc` + `@Transactional` rolls back each test's rows.
- Broke: (1) The app wouldn't start: `FATAL: invalid value for parameter "TimeZone": "Asia/Calcutta"`. Windows gives Java the old zone name, and Postgres 16 only knows `Asia/Kolkata`. Fix: run the JVM in UTC (`TimeZone.setDefault` in `main` + `-Duser.timezone=UTC` for surefire); servers use UTC anyway. (2) `@WebMvcTest` broke, because the service now needs a `WalletRepository`, which the web-only slice doesn't load. (3) `GET /wallets/does-not-exist` returned 400: `UUID.fromString` threw `IllegalArgumentException` before the database was asked. I chose 404 (catch it and throw `WalletNotFoundException`), because the client shouldn't need to know ids are UUIDs. (4) `V2`: `id` had no type, `UNIQUE` duplicated `PRIMARY KEY`, and `balance > 0` would have rejected a 0 balance.
- Next time: When Maven says `BUILD FAILURE`, scroll up to the `Caused by:` lines; the real reason is there. Get a migration right *before* the first run. Use Spring's `@Transactional` (`org.springframework...`), not `jakarta.transaction`. Skipped the break-it experiments; revisit C (removing `@Transactional`) before Day 9's posting engine.

## Day 7 · Nov 14: Docker Compose + generating ledger-service
- Learned: An **image** is a read-only template (like a class); a **container** is a running copy (like an object). A **port mapping** `5432:5432` is `host:container`. A **volume** stores data outside the container, so `docker compose down` (removes the containers) keeps every database, while `down -v` also deletes the volume and wipes them. **Compose** describes all containers in one YAML file, so `docker compose up -d` replaces long `docker run` commands. `infra/docker-compose.yml` runs `postgres:16` with a named volume, a healthcheck (`pg_isready`), and an init script that creates `ledger_db`, `payments_db`, `bank_db` and `identity_db` (one database per service). **Init scripts and `POSTGRES_USER`/`POSTGRES_PASSWORD` only run when the data volume is empty**, i.e. on the first start; afterwards Postgres sees existing data and skips them, so changing `.env` later does nothing until `down -v`. **`.env`** holds the real values and is git-ignored; **`.env.example`** is committed so someone cloning the repo knows which variables to set. Generated `services/ledger-service` (Web, Data JPA, PostgreSQL, Flyway, Validation, Actuator, plus springdoc by hand). `${DB_USER:user}` in properties means "env var, or this default", so the same code later runs inside Compose with `DB_HOST=postgres`. `/actuator/health` shows UP with a `db` component; Swagger UI loads (empty until Day 10).
- Broke: (1) `psql -U kosh` gave `role "kosh" does not exist`: my `.env` uses a different user, and Postgres only creates the role named in `POSTGRES_USER`. (2) `spring-boot:run` failed with `password authentication failed for user "kosh"`: the property defaults didn't match `.env`. The error was reported by `flywayInitializer`, because Flyway is the first thing to touch the database at startup, so connection problems usually show up as Flyway errors. (3) A new app needs the UTC time-zone fix again (`main` + surefire `argLine`).
- Next time: When credentials change, check every place that uses them (`.env`, properties, psql commands). When a startup error names Flyway, check the connection settings first. Read `git status` before committing; it showed 36 lines missing from the README.

## Day 8 · Nov 16: Ledger schema, entities, repositories
- Learned: Wrote `V1__ledger_core.sql` (account, journal_entry, posting, balance) and `V2__system_accounts.sql` myself, from the doc's requirements. UUID ids with `DEFAULT gen_random_uuid()`, so plain-SQL migrations can insert rows without Java. `request_id` is `TEXT` because the client creates it; `correlation_id` is `TEXT` because it arrives from outside in any format. **Partial unique index** `one_account_per_system_type ON account (type) WHERE type IN (...)` allows exactly one of each system account; `UNIQUE (owner_id, type)` would not work, because in Postgres **two NULLs are not equal**, so system accounts (owner NULL) would slip through. V2 fills `balance` with `INSERT ... SELECT id, true FROM account WHERE ...`, because the ids are random and can't be typed. **Entities:** `@Enumerated(EnumType.STRING)` stores the name, not the position (adding an enum value in the middle would otherwise silently change old rows). Entry ↔ posting is a real link: `@ManyToOne(LAZY)` + `@JoinColumn("entry_id")` on Posting (the side that owns the column), `@OneToMany(mappedBy = "entry", cascade = PERSIST)` on JournalEntry; `addPosting` sets both ends so `entry_id` can't be NULL. Posting → account is just `UUID accountId`: a posting is *part of* its entry but only *points to* its account, and a `@ManyToOne Account` would load an account per posting (the N+1 problem) while the SQL foreign key already guarantees it exists. `Balance` has `@Id` with no `@GeneratedValue` (it reuses the account's id) and no debit/credit methods, because money changes only through the guarded UPDATE (Day 9). **Repositories:** Spring writes the class from the interface; `findByType` / `findByRequestId` get their SQL from the method name; `Optional` means "0 or 1 row", which is only safe because of the unique index.
- Broke: (1) V1: `PRIMARY KEY gen_random_uuid()` without `DEFAULT`, a column with no type, `balance` without a primary key, nullable posting links, `owner_id NOT NULL` (system accounts have no owner), `request_id BIGINT`. (2) V2: spaces instead of underscores (`'BANK CLEARING'`), which my own CHECK rejected; `SELECT account_id FROM account` (the column is `id`); 2 columns named but 1 value selected; and `WHERE type = 'CUSTOMER WALLET'`, which would have inserted **0 balance rows with no error**. (3) Repositories in `com.kosh.repository`, outside `com.kosh.ledger`: `@SpringBootApplication` only scans its own package and below, so Spring would never create them. The app still started, because nothing used them yet; it would have failed on Day 9 with "No qualifying bean". Confirmed by the startup log: "Found 4 JPA repository interfaces".
- Next time: Dry-run a migration in `BEGIN; ... ROLLBACK;` before Flyway applies it. After every INSERT ... SELECT, check the row count. Keep every class under the main application's package.
